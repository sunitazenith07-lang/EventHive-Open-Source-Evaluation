  - `tests/test_acceptance_matrix.py` and `tests/test_contract.py`: Comprehensive acceptance suites defining contract requirements.
- **Order lifecycle or data flow traced:**
  - Initial state: `status="PLACED"`, `payment_status="UNPAID"`.
  - Payment: `payment_confirmed` transitions `payment_status` to `"PAID"`. If the order was already rejected or cancelled, it sets `refund_due_paise = total_paise`.
  - Restaurant decision: `restaurant_accepted` moves order to `"ACCEPTED"`; `restaurant_rejected` moves order to `"REJECTED"`, setting `refund_due_paise = total_paise` if paid.
  - Customer cancellation: Allowed only in `"PLACED"` or `"ACCEPTED"` states; moves to `"CANCELLED"`, setting `refund_due_paise = total_paise` if paid. Cancellations attempted in `"OUT_FOR_DELIVERY"` or `"DELIVERED"` are strictly rejected.
  - Fulfillment: `dispatch_started` transitions `"ACCEPTED"` to `"OUT_FOR_DELIVERY"`; `order_delivered` transitions `"OUT_FOR_DELIVERY"` to `"DELIVERED"`.
  - Refunds: `refund_processed` applies strictly to eligible orders (`"REJECTED"` or `"CANCELLED"` with `"PAID"` payment status and positive `refund_due_paise`). Amount must be a positive integer and cannot exceed `refund_due_paise - refunded_paise`. Payment status becomes `"REFUNDED"` only upon full refund.
  - Reconciliation: Compares internal and provider records by `order_id` in deterministic sorted order, reporting missing records, amount mismatches, and status mismatches independently.

## 3. Investigation and implementation strategy
- **Issue 1: Missing event idempotency in `apply_order_event`**
  - *Observed symptom:* 20 parameterized tests in `test_payment_event_replay_idempotent` (`EV-000` through `EV-019`) and `test_duplicate_event_is_idempotent` failed because replaying an event appended duplicate IDs (`['EV-000', 'EV-000'] != ['EV-000']`) and reapplied state modifications.
  - *Hypothesis tested:* If `event_id` is already in `order["processed_event_ids"]`, `apply_order_event` should immediately return the unmutated order copy.
  - *Evidence:* Lines 16-43 in starter `service.py` lacked an early return check on `event_id in out["processed_event_ids"]`.
  - *Fix chosen:* Checked `if event_id is not None and event_id in out["processed_event_ids"]: return out`, and appended `event_id` to `processed_event_ids` only once upon successful processing.

- **Issue 2: Unsafe refund validation, eligibility, and overflow**
  - *Observed symptom:* 32 tests failed across `test_invalid_refund_amounts_are_ignored` (15 failures), `test_refund_eligibility_matrix` (10 failures), and `test_refunds_cannot_exceed_due` (7 failures).
  - *Hypothesis tested:* Starter code blindly executed `out["refunded_paise"] += event.get("amount_paise", 0)` without validating order eligibility, data types, positivity, or bounds.
  - *Evidence:* Non-integer amounts (e.g. `True`, `0.5`, `"10"`), negative values, refunds to `PLACED`/`ACCEPTED` orders, and refunds exceeding `refund_due_paise` were processed.
  - *Fix chosen:* Added strict checks:
    1. Amount validation: `type(amount) is int and amount > 0` (preventing `bool`, floats, strings, and zero/negative numbers).
    2. Eligibility check: `out.get("status") in ("REJECTED", "CANCELLED") and out.get("payment_status") == "PAID" and out.get("refund_due_paise", 0) > 0`.
    3. Bound check: `amount <= (out.get("refund_due_paise", 0) - out.get("refunded_paise", 0))`.
    4. Status update: Transition to `"REFUNDED"` only when `out["refunded_paise"] == out.get("refund_due_paise", 0)`.

- **Issue 3: Reconciliation engine omitted status checks and key alignment**
  - *Observed symptom:* 7 status mismatch tests failed (`test_reconciliation_status_mismatch_matrix`) and `main.py` falsely reported `ORD-101` and `ORD-102` as amount mismatches instead of matching or status mismatching.
  - *Hypothesis tested:* Starter `reconcile_orders` never checked `a.get("status") != b.get("status")` and assumed all non-amount mismatches were `matched`. In addition, internal order dicts use `total_paise` whereas provider records use `amount_paise`.
  - *Evidence:* Lines 59-64 in starter `service.py`:
    ```python
    if a.get("amount_paise") != b.get("amount_paise"):
        report["amount_mismatches"].append(key)
    else:
        report["matched"].append(key)
    ```
  - *Fix chosen:* Evaluated both `amount_mismatch` and `status_mismatch` independently. Resolved amount keys via `r.get("amount_paise") if "amount_paise" in r else r.get("total_paise")`. If amount mismatches, record in `amount_mismatches`; if status mismatches, record in `status_mismatches`; if both mismatch, record in both lists; only record in `matched` when neither mismatches.

## 4. Implementation decisions
- **Main changes and why:**
  - Maintained pure function architecture using `deepcopy` to guarantee inputs are never mutated.
  - Used `type(amount) is int` rather than `isinstance(amount, int)` because in Python `isinstance(True, int)` evaluates to `True`, which would allow boolean values to be treated as 1 paise.
  - Handled late `payment_confirmed` events on already `CANCELLED` or `REJECTED` orders to ensure `refund_due_paise` is initialized if payment arrives out-of-order.
- **Alternatives considered and why rejected:**
  - *Alternative: Raising exceptions on invalid events or duplicate event IDs.* Rejected because the problem statement specifies: "Handle empty input, missing fields, unknown IDs, invalid event types and duplicates without corrupting state." The service contract expects safe, non-destructive no-ops rather than unhandled exceptions.
  - *Alternative: In-place mutation of input orders.* Rejected because `test_input_order_is_not_mutated` explicitly asserts that the input dictionary remains strictly unmodified.
- **Assumptions:**
  - `total_paise` represents the internal payable amount on order creation.
  - An event with `event_id=None` or an unknown event type should not mutate state.
  - Partial refunds remain in `payment_status="PAID"` until the entire `refund_due_paise` has been reimbursed.
